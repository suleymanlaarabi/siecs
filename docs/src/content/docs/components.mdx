import { Tabs, TabItem } from '@astrojs/starlight/components';

Components are data types registered in a world. They can be used through typed
macros or directly through `ecs_component_t` ids.

Resources use a separate id space and are stored once per world instead of once
per entity. Use a component for per-entity data, and a resource for unique world
state such as time, input, renderer state, or shared config.

## Typed components

Components are declared once and registered with each world:

<Tabs syncKey="language">
<TabItem label="C">

```c
ECS_COMPONENT_DECLARE(Position, {
    float x;
    float y;
});

ECS_COMPONENT_DEFINE(Position);
ECS_COMPONENT_REGISTER(Position);
```

</TabItem>
<TabItem label="C++">

```cpp
// Position is declared with ECS_COMPONENT_DECLARE in a shared C header.
#include "components.h"

ecs::init();
auto entity = ecs::entity::create();
entity.set(Position{ .x = 1.0f, .y = 2.0f });
auto position_id = ecs::component<Position>();
```

</TabItem>
</Tabs>

In C++, a type declared with `ECS_COMPONENT_DECLARE` uses the same C id and
descriptor automatically; no second component registration is created. Plain
C++ structs can still be registered automatically on first use. Use the
`reflected(...)` declaration when a native C++ type's fields must be visible to
the REST explorer or JSON serialization:

```cpp
struct Position {
    reflected(float x; float y;);
};
```

When a shared C declaration also needs C++-only methods, use
`ECS_COMPONENT_DECLARE_CPP`:

```cpp
ECS_COMPONENT_DECLARE_CPP(Position,
    ECS_CPP_FIELDS(
        float x;
        float y;
    ),
    ECS_CPP_METHODS(
        void reset() { x = 0.0f; y = 0.0f; }
        float length_squared() const { return x * x + y * y; }
    )
);
```

The same header remains valid C: the method block is omitted and the C layout,
id, descriptor, and reflection metadata remain unchanged. C++ methods must not
add instance data.

## Set and Read

`ecs_set()` adds the component if needed, then writes the value:

<Tabs syncKey="language">
<TabItem label="C">
```c
ecs_set(entity, Position, { .x = 1.0f, .y = 2.0f });
```
</TabItem>
<TabItem label="C++">
```cpp
entity.set(Position{ .x = 1.0f, .y = 2.0f });
```
</TabItem>
</Tabs>

`ecs_get()` and `entity.get<T>()` assume the component exists:

<Tabs syncKey="language">
<TabItem label="C">
```c
Position *position = ecs_get(entity, Position);
position->x += 1.0f;
```
</TabItem>
<TabItem label="C++">
```cpp
Position &position = entity.get<Position>();
position.x += 1.0f;
```
</TabItem>
</Tabs>

When the component may be absent, use the nullable helpers:

<Tabs syncKey="language">
<TabItem label="C">
```c
Position *position = ecs_try_get(entity, Position);
if (position != NULL) position->x += 1.0f;
```
</TabItem>
<TabItem label="C++">
```cpp
if (Position *position = entity.try_get<Position>()) {
    position->x += 1.0f;
}
```
</TabItem>
</Tabs>

## Add, remove, and check components

Use the typed operation for components that do not need an immediate value:

<Tabs syncKey="language">
<TabItem label="C">
```c
ecs_add(entity, Position);
```
</TabItem>
<TabItem label="C++">
```cpp
entity.add<Position>();
```
</TabItem>
</Tabs>

The C++ methods accept several component types or values at once:

```cpp
entity.set(Position{ 1.0f, 2.0f }, Velocity{ 3.0f, 4.0f });
entity.add<Selected, Visible>();

if (entity.has<Selected, Visible>()) {
    entity.remove<Selected, Visible>();
}
```

Multi-component `set`, `add`, and `remove` calls are deferred as one batch. This
lets SIECS compute the final archetype and migrate the entity once instead of
once per component.

Check and remove components with:

<Tabs syncKey="language">
<TabItem label="C">
```c
if (ecs_has(entity, Position)) {
    ecs_remove(entity, Position);
}
```
</TabItem>
<TabItem label="C++">
```cpp
if (entity.has<Position>()) {
    entity.remove<Position>();
}
```
</TabItem>
</Tabs>

Removing a component that is not present is a no-op.

## Disabled

`Disabled` is a built-in component. Adding it to an entity excludes that entity
from queries by default:

<Tabs syncKey="language">
<TabItem label="C">
```c
ecs_add(entity, Disabled);
```
</TabItem>
<TabItem label="C++">
```cpp
entity.disable();
```
</TabItem>
</Tabs>

Queries, systems, and observers skip disabled entities by default. To match them
explicitly:

<Tabs syncKey="language">
<TabItem label="C">
```c
ecs_query({
    .terms = { ecs_in(Position), ecs_filter(Disabled) },
});
```
</TabItem>
<TabItem label="C++">
```cpp
ecs::query().require<Position>().require<Disabled>().each(
    [](Position &position) { position.x += 1.0f; });
```
</TabItem>
</Tabs>

## Component requirements

Use `ecs_with()` when adding one component should also add another component:

<Tabs syncKey="language">
<TabItem label="C">
```c
ecs_with(ecs_id(Renderable), ecs_id(Transform));

ecs_add(entity, Renderable);

/* Transform was added first. */
```
</TabItem>
<TabItem label="C++">
```cpp
ecs::component_requires<Renderable, Transform>();
entity.add<Renderable>();
```
</TabItem>
</Tabs>

This only affects future adds. It does not rewrite existing entities.

Requirement cycles are invalid. In debug builds, cycles are asserted when
calling `ecs_with()`.

## ID-based components

For generic code, register a component from a descriptor:

<Tabs syncKey="language">
<TabItem label="C">
```c
typedef struct {
    float x;
    float y;
} Position;

ecs_component_t position_id = ecs_component({
    .name = "Position",
    .size = sizeof(Position),
});
```
</TabItem>
<TabItem label="C++">
```cpp
auto position_id = ecs::component<Position>();
```
</TabItem>
</Tabs>

Then use the `_cid` functions:

<Tabs syncKey="language">
<TabItem label="C">
```c
ecs_set_cid(entity, position_id, &(Position){ .x = 1.0f, .y = 2.0f });

Position *position = ecs_get_cid(entity, position_id);
```
</TabItem>
<TabItem label="C++">
```cpp
Position value{ .x = 1.0f, .y = 2.0f };
entity.set(value);
auto &position = entity.get<Position>();
```
</TabItem>
</Tabs>

## Reflection and JSON

Typed component macros register reflection metadata through `sireflect` and
`sijson`:

<Tabs syncKey="language">
<TabItem label="C">
```c
ECS_COMPONENT(Position, {
    float x;
    float y;
});
```
</TabItem>
<TabItem label="C++">
```cpp
struct Position {
    reflected(float x; float y;);
};
```
</TabItem>
</Tabs>

That metadata is used by the REST explorer to list component schemas and
serialize reflected component values. Components registered only with a raw
descriptor are reflected only when `struct_desc` points to a valid
`sireflect_struct_desc_t` produced by the reflection layer:

<Tabs syncKey="language">
<TabItem label="C">
```c
ecs_component_t position_id = ecs_component({
    .name = "Position",
    .size = sizeof(Position),
    .struct_desc = position_reflection_desc,
});
```
</TabItem>
<TabItem label="C++">
```cpp
auto position_id = ecs::component<Position>();
```
</TabItem>
</Tabs>

The C++ wrapper creates reflection metadata from `reflected(...)` declarations.
For a runtime descriptor assembled dynamically, use the C descriptor API from
C++.

If a component has no reflection metadata, SIECS can still store and query it,
but the REST explorer cannot show or edit its fields.

Plain C++ structs are stored and queried normally, but have no reflected fields
unless they use `reflected(...)`.

## Hooks

Component descriptors can provide lifecycle hooks:

<Tabs syncKey="language">
<TabItem label="C">
```c
#include <stdio.h>

static void on_set_position(
    ecs_entity_t entity,
    ecs_component_t component,
    const void *new_value,
    void *current_value
) {
    const Position *incoming = new_value;
    Position *stored = current_value;
    printf("old=%f new=%f", stored->x, incoming->x);
}
```
</TabItem>
<TabItem label="C++">
```cpp
#include <cstdio>

static void on_set_position(ecs_entity_t, const Position &incoming, Position &stored) {
    std::printf("old=%f new=%f", stored.x, incoming.x);
}

ecs::component_hooks<Position> hooks{ .on_set = on_set_position };
auto position_id = ecs::component(hooks);
```
</TabItem>
</Tabs>

`on_set` receives the new value passed to `ecs_set()` or `ecs_set_cid()`. The
stored value is still the previous value until the hook returns.

`on_add` receives zero-initialized storage after the component is added.
`on_remove` receives the value that is about to be removed.
