A structural change changes the shape of ECS storage.

This is one of the most important distinctions in an archetype ECS because structural mutation has a different cost and safety model from ordinary value mutation.

## Value mutation versus structural mutation

Suppose an entity owns:

```text
Position + Velocity
```

Changing:

```text
Position.x = 10
```

modifies bytes in the existing `Position` column.

The entity stays in the same archetype, table, and normally the same row.

Now add `Health`:

```text
before: {Position, Velocity}
after:  {Position, Velocity, Health}
```

The entity no longer belongs to the same archetype.

It has to migrate to the table representing the new component set.

That is a structural change.

## Common structural operations

Operations that can change structure include:

- adding a component;
- removing a component;
- setting a component that is currently absent;
- adding or removing a tag;
- changing table-defining relation state;
- adding inherited structure;
- destroying an entity.

Operations that only modify an already-present ordinary component value are not structural in the same sense.

## Conceptual migration algorithm

When an entity moves from:

```text
A = {Position, Velocity}
```

to:

```text
B = {Position, Velocity, Health}
```

a migration conceptually requires:

1. identify the destination archetype/table;
2. reserve a row in the destination table;
3. preserve or move components shared by both structures;
4. initialize the newly added component;
5. run relevant lifecycle hooks/events;
6. remove the old row from the source table;
7. update the entity record to point at the destination row;
8. maintain query/observer/relation metadata as required.

SIECS can optimize the path, but it cannot reduce the operation to a single field write because the entity's storage schema changed.

## Removal is also migration

Removing `Velocity` from:

```text
{Position, Velocity, Health}
```

produces:

```text
{Position, Health}
```

The entity must move to the destination table, while the removed component may need destruction/lifecycle work.

A remove is therefore not simply:

```text
delete one field from the row
```

because all rows in one table must retain the same structure.

## Setting an absent component is structural

A `set` operation can have two different cost shapes.

### Component already present

```text
set Position
```

updates the existing column value.

### Component absent

```text
set Health
```

must first make `Health` part of the entity's structure, then initialize/set the value.

This is why APIs such as `set` can hide a structural transition depending on current membership.

When performance matters, know whether the component is already present.

## Tags have structural cost

Because tags participate in the archetype, toggling a tag is a migration.

Example:

```text
{Position, Velocity}
        ↕ Selected
{Position, Velocity, Selected}
```

For user-driven selection changes, this may be trivial.

For a state toggled every frame across a huge population, it may become a dominant cost.

The value-versus-structure decision should reflect change frequency.

## Structural changes invalidate storage assumptions

Suppose a query is processing:

If code immediately adds a component to one of those entities and the mutation is applied in place, that entity can move to another table and source rows can compact.

The previously acquired pointers/row indices may no longer describe the same storage.

This is why structural mutation during iteration requires a defined policy.

## Deferred mutation

SIECS provides an explicit command buffer using:

<Tabs syncKey="language">
<TabItem label="C">

```c
ecs_defer_begin();
/* mutations */
ecs_defer_end();
```

</TabItem>
<TabItem label="C++">

```cpp
ecs::system("StructuralWork")
    .each([](ecs::entity entity) {
        // Structural entity operations are deferred during system iteration.
        entity.add<Selected>();
    });
```

</TabItem>
</Tabs>

The outermost `ecs_defer_end()` flushes queued commands.

Normal SIECS systems are also wrapped in deferred execution unless configured for the special non-deferred mode that does not iterate entity queries.

The important behavior is:

```text
iterate stable batch
    ↓
record structural intent
    ↓
finish safe iteration region
    ↓
flush commands
    ↓
perform migrations
```

This separates **what the system wants to change** from **when table storage is mutated**.

## Why deferring is more than pointer protection

Deferring structural work has several benefits:

- current iterator storage can remain stable;
- repeated edits can sometimes be combined or coalesced;
- mutation order becomes explicit at a synchronization point;
- observer/event behavior can be associated with command application;
- systems can express structural intent without manually staging entity lists.

It also introduces semantics that need to be understood: a deferred write may not be physically visible in table storage until the buffer is flushed.

## Deferred operations are not asynchronous work

Deferring does not mean the change runs later on an arbitrary background thread.

It means the world records the mutation and applies it at a controlled boundary.

Think:

```text
transactional staging
```

rather than:

```text
background job
```

This distinction matters for reasoning about system order.

## Nested defer scopes

SIECS tracks defer depth.

Nested scopes can record into the same command-buffer context, with the outermost end performing the flush.

Conceptually:

```text
defer begin  depth 1
  defer begin depth 2
  defer end   depth 1
  // still deferred
defer end     depth 0
  // flush
```

This allows helpers to safely create their own defer scope without necessarily forcing an early flush inside an already deferred operation.

## Batched structural intent

Suppose an entity needs three new components.

Naively:

```text
A
 -> A+B
 -> A+B+C
 -> A+B+C+D
```

can require multiple migrations.

If the final structure is known, a batch operation can compute:

```text
A
 -> A+B+C+D
```

and migrate once.

SIECS's C++ multi-component `set`, `add`, and `remove` operations use deferred batching so the final archetype can be reached with fewer transitions.

This is an important SIECS-specific optimization and a general ECS design principle:

> Express one logical structural transition as one batch when possible.

## Command coalescing

Some deferred operations can be coalesced to a final state.

For example, SIECS relation documentation describes deferred changes to one relation being coalesced to the final target.

The broader lesson is that command-buffer semantics can differ from immediately applying every intermediate state.

Do not write code that depends on observing all intermediate deferred table shapes unless the API explicitly guarantees that behavior.

## Lifecycle hooks and structural cost

Components may have lifecycle hooks such as add, set, and remove behavior.

Structural mutation therefore may execute application-defined work in addition to moving memory.

When measuring migration cost, include:

```text
lookup/transition
+ allocation/growth
+ value move/copy/init
+ hooks/events
+ row removal/compaction
+ metadata updates
```

A component with expensive constructors/destructors or callbacks can make migration much more costly than its byte size suggests.

## Large components make migration heavier

If an entity carries a 1 KB component and changes archetype frequently, structural moves may transfer or construct significant data.

A large cold payload that does not need to participate directly in table migration may be better represented by a compact handle to external storage.

This is not a blanket rule. It is a reminder that component layout and structural frequency interact.

## Structural state machines

A useful way to design ECS mutation is to think in named structural states.

Example:

```text
Alive
    Position
    Velocity
    Health
    Character

Dead
    Position
    Corpse
    DecayTimer

Removed
    entity destroyed
```

Then transitions are deliberate:

```text
Alive -> Dead
Dead  -> Removed
```

This is clearer than scattering unrelated add/remove calls throughout many systems.

It also makes expected archetypes and migration frequency easier to review.

## Structural change as semantic change

Adding/removing a component often changes which systems match the entity.

That means structure is not only a storage concern.

Example:

```text
add Disabled
```

can remove the entity from normal query/system participation.

Adding `Selected` can make editor systems begin matching it.

Removing `Velocity` can remove it from movement systems.

Therefore structural mutations are part of program semantics and execution flow.

## Value state may be better when participation does not change

Suppose a damage system processes all characters and checks a health mode:

<Tabs syncKey="language">
<TabItem label="C">

```c
health->state = Invulnerable;
```

</TabItem>
<TabItem label="C++">

```cpp
health.state = Invulnerable;
```

</TabItem>
</Tabs>

If every health-related system still needs to visit the entity, creating a structural `Invulnerable` tag may not improve selection enough to justify migration.

A value is often better when the same systems continue to own the data.

Structure is useful when the change should alter query membership.

## Structural events and observers

SIECS observers can react to lifecycle and relation events.

This makes structural changes observable:

```text
OnAdd
OnRemove
OnSet
relation set/remove events
```

Observers are useful for maintaining derived state or reacting to transitions.

However, observers also add work to mutations.

A design with huge volumes of structural churn plus many observers should be profiled as a combined system.

## Destroying entities during iteration

Destruction removes an entity from storage and invalidates its handle.

When destruction occurs through the deferred path, a system can record the intent safely and let the command buffer apply it after the iteration region.

This avoids manually reasoning about swapped rows while the loop is still advancing.

The pattern is:

```text
for matching entities:
    if should_die:
        request kill

flush later
```

rather than mutating the backing table under the active loop.

## Structural synchronization points

A deferred architecture introduces synchronization points where staged structural state becomes real.

Important questions include:

- when does the current system's command buffer flush?
- can a later system in the phase see the new structure?
- when are observers invoked?
- what state is visible to manual queries executed inside the same deferred scope?

Those exact answers belong in system/observer manuals, but the theory is simple:

> Deferred structural mutation creates a before/after boundary in world structure.

System design should be explicit about that boundary.

## Structural churn metrics

If migration performance matters, profile more than total frame time.

Useful counters include:

- adds per frame;
- removes per frame;
- kills/spawns per frame;
- rows migrated;
- bytes moved by migrated components;
- tables created;
- average table population;
- command-buffer size;
- observer events emitted;
- time spent flushing commands.

A world can have excellent query iteration while still spending too much time changing structure.

## Avoid “component ping-pong”

A common anti-pattern is toggling between two archetypes every frame:

```text
A -> A+Tag -> A -> A+Tag -> ...
```

If the tag only represents a transient algorithm state, consider a stable value or explicit work queue.

Structural state is most valuable when it persists long enough for queries to benefit from it.

## Structural changes are not forbidden

Do not over-optimize by eliminating all add/remove operations.

ECS composition is useful precisely because entities can change capabilities.

Good structural changes include:

- spawning an entity into its intended shape;
- transitioning from alive to dead;
- adding a long-lived feature;
- removing a subsystem role;
- changing stable parent/group relationships;
- editor actions;
- rare mode transitions.

The goal is to make structural work **meaningful**.

## Common mistakes

### Calling every mutation “just a field update”

Adding an absent component changes storage shape.

### Performing immediate structural edits through active field pointers

Use documented deferred/safe patterns.

### Toggling structural tags at high frequency without measuring

A value field may fit better.

### Splitting one transition into many sequential add/removes

Batch the final structural intent when possible.

### Ignoring hooks and observer work in migration cost

Application callbacks can dominate raw memory movement.

### Assuming deferred commands are visible immediately

Understand flush boundaries.

## The rule to remember

```text
value change
    = modify data inside current structure

structural change
    = change which structure owns the entity
```

The second operation is more powerful and more expensive. Use it when the structure itself is meaningful.
