This quickstart introduces the concepts that appear throughout the SIECS manuals.
It is intentionally broad: each section shows the smallest useful example and
connects it to the rest of the runtime.

SIECS is an archetype ECS written in C17 with a typed C++20 API. Both APIs use
the same runtime and the same active world.

## Building SIECS

The standalone distribution consists of `siecs.h` and `siecs.c`.

<Tabs syncKey="language">
<TabItem label="C">

```sh
cc -std=c17 -I. main.c siecs.c -pthread -o app
```

</TabItem>
<TabItem label="C++">

```sh
cc -std=c17 -I. -c siecs.c -o siecs.o
c++ -std=c++20 -I. main.cpp siecs.o -pthread -o app
```

</TabItem>
</Tabs>

The C++ API is header-only but links to the same C runtime. See
[Building SIECS](../building/) for Bake integration and platform notes.

## Concepts

### World

The world owns ECS state. Initialize it before registering types or creating
entities and finalize it after all ECS work has stopped.

<Tabs syncKey="language">
<TabItem label="C">

```c
#include <siecs.h>

int main(void) {
    ecs_init();

    /* application */

    ecs_fini();
    return 0;
}
```

</TabItem>
<TabItem label="C++">

```cpp
#include <siecs.h>

int main() {
    ecs::init();

    // application

    ecs::fini();
}
```

</TabItem>
</Tabs>

SIECS currently exposes one active world at a time. Handles, query ids, system
ids, component ids and resource ids belong to that active world.

`ecs_init_w_features()` configures world features such as frame limiting and
worker threads:

```c
ecs_init_w_features(&(ecs_world_feat_desc_t){
    .target_fps = 60,
    .worker_threads = ECS_WORKERS_AUTO,
});
```

### Entity

An entity is an identity. It does not imply a class or object layout.

```c
ecs_entity_t e = ecs_new();
```

```cpp
auto e = ecs::entity::create();
```

An entity starts alive with no user components. `ecs_kill()` destroys it.

SIECS entity handles are 64-bit values containing an entity index and a
generation. The generation changes when a recycled index is reused, which lets
the runtime reject stale handles.

### Id

SIECS uses separate id spaces for different kinds of registered objects:

- `ecs_component_t` for components and tags;
- `ecs_relation_id_t` for relations;
- `ecs_resource_t` for resources;
- `ecs_query_id_t` for queries;
- `ecs_system_id_t` for systems;
- `ecs_observer_id_t` for observers;
- `ecs_module_id_t` for modules.

An entity handle is not interchangeable with a component or relation id.

This is an important difference from ECS APIs that model most concepts through
a single universal id namespace.

### Component

A component is per-entity data.

<Tabs syncKey="language">
<TabItem label="C">

```c
ECS_COMPONENT(Position, {
    float x;
    float y;
});

ECS_COMPONENT_REGISTER(Position);

ecs_entity_t e = ecs_new();
ecs_set(e, Position, { .x = 10, .y = 20 });
```

</TabItem>
<TabItem label="C++">

```cpp
struct Position {
    float x;
    float y;
};

auto e = ecs::entity::create();
e.set(Position{10, 20});
```

</TabItem>
</Tabs>

Entities with the same owned component set are stored together in the same
archetype table.

### Tag

A tag is a component with no payload. It contributes to an entity's structure
and can be used by queries.

<Tabs syncKey="language">
<TabItem label="C">

```c
ECS_TAG(Enemy);
ECS_COMPONENT_REGISTER(Enemy);

ecs_add(e, Enemy);
```

</TabItem>
<TabItem label="C++">

```cpp
struct Enemy {};
e.add<Enemy>();
```

</TabItem>
</Tabs>

Tags do not allocate a data column, but adding or removing one is still a
structural change because it moves the entity to another archetype.

### Relation

Relations connect a source entity to a target entity.

```c
ecs_relate(child, ChildOf, parent);
```

```cpp
child.child_of(parent);
```

SIECS relations use a separate relation registry and support three storage
modes:

- `EcsRelationDense` stores a target per source row;
- `EcsRelationByDepth` additionally maintains hierarchy depth information;
- `EcsRelationByTarget` groups sources by target for fast target-filtered queries.

The storage mode determines which query operations are efficient and valid.

### Hierarchies

`ChildOf` is the built-in hierarchy relation.

```c
ecs_relate(child, ChildOf, parent);
```

Killing a parent recursively cleans up its owned `ChildOf` subtree. Hierarchy
queries can order matching tables by depth when the relation uses
`EcsRelationByDepth`.

### Type

In an archetype ECS, an entity's structural type is the exact set of components
and structural relations that determine its table.

Conceptually:

```text
{Position, Velocity}
{Position, Velocity, Enemy}
{Position, Health}
```

are three different structural types and therefore three different archetypes.

Applications do not normally manipulate an `ecs_type_t` directly. Structural
types are created by adding, removing and relating data.

### Resource

A resource is one typed value for the whole world.

```c
ECS_RESOURCE(Time, {
    float dt;
});
ECS_RESOURCE_REGISTER(Time);
ecs_set_resource(Time, { .dt = 1.0f / 60.0f });
```

Resources are not components and are not stored on entities. Systems can declare
resource access so the scheduler can reason about dependencies.

### Query

A query matches archetype tables.

```c
ecs_query_id_t q = ecs_query({
    .components = {
        ecs_inout(Position),
        ecs_in(Velocity),
    },
});
```

Iterating a query yields non-empty table batches:

```c
ecs_iter_t it = ecs_query_iter(q);
while (ecs_iter_next(&it)) {
    Position *p = ecs_field(&it, 0);
    const Velocity *v = ecs_field(&it, 1);

    for (uint32_t i = 0; i < it.count; i++) {
        p[i].x += v[i].x;
        p[i].y += v[i].y;
    }
}
ecs_query_fini(q);
```

Persistent queries cache matching tables. They do not rebuild a list of matching
entities on every iteration.

### System

A system is a persistent query plus a callback and scheduling metadata.

```c
static void Move(ecs_iter_t *it) {
    Position *p = ecs_field(it, 0);
    const Velocity *v = ecs_field(it, 1);

    for (uint32_t i = 0; i < it->count; i++) {
        p[i].x += v[i].x * it->delta_time;
        p[i].y += v[i].y * it->delta_time;
    }
}

ecs_system({
    .name = "Move",
    .phase = EcsOnUpdate,
    .query.components = {
        ecs_inout(Position),
        ecs_in(Velocity),
    },
    .callback = Move,
});
```

`ecs_progress()` executes enabled systems in phase order.

### Phase

Phases define broad ordering groups for systems.

SIECS provides built-in phases for startup, loading, update and rendering. The
main recurring sequence includes:

```text
EcsOnLoad
EcsPostLoad
EcsPreUpdate
EcsOnUpdate
EcsPostUpdate
EcsPreRender
EcsOnRender
EcsPostRender
```

Custom phases can be inserted before or after existing phases. Systems inside
one phase can also use `.after` dependencies.

### Observer

Observers react to events instead of running each frame.

```c
static void OnPositionSet(ecs_observer_event_t *event) {
    const Position *value = event->trigger_data;
    (void)value;
}

ecs_observer({
    .on = EcsOnSet,
    .query.components = { ecs_in(Position) },
    .callback = OnPositionSet,
});
```

Built-in observer events cover component add, remove and set, and relation
changes. Applications can also register custom events.

### Module

A module groups registrations behind one import operation.

Modules can capture components, systems and observers created while the module
is imported. Disabling a module disables its captured systems and observers
without unregistering component types or deleting entity data.

## A complete minimal example

The following combines the main ideas into one small program.

<Tabs syncKey="language">
<TabItem label="C">

```c
#include <siecs.h>

ECS_COMPONENT(Position, { float x; float y; });
ECS_COMPONENT(Velocity, { float x; float y; });

static void Move(ecs_iter_t *it) {
    Position *p = ecs_field(it, 0);
    const Velocity *v = ecs_field(it, 1);

    for (uint32_t i = 0; i < it->count; i++) {
        p[i].x += v[i].x * it->delta_time;
        p[i].y += v[i].y * it->delta_time;
    }
}

int main(void) {
    ecs_init();

    ECS_COMPONENT_REGISTER(Position);
    ECS_COMPONENT_REGISTER(Velocity);

    ecs_system({
        .name = "Move",
        .phase = EcsOnUpdate,
        .query.components = {
            ecs_inout(Position),
            ecs_in(Velocity),
        },
        .callback = Move,
    });

    ecs_entity_t e = ecs_new();
    ecs_set(e, Position, {0, 0});
    ecs_set(e, Velocity, {1, 0});

    ecs_progress();

    const Position *p = ecs_get(e, Position);

    ecs_fini();
    return p != NULL ? 0 : 1;
}
```

</TabItem>
<TabItem label="C++">

```cpp
#include <siecs.h>

struct Position { float x, y; };
struct Velocity { float x, y; };

int main() {
    ecs::init();

    ecs::system("Move")
        .phase(EcsOnUpdate)
        .each([](Position &p, const Velocity &v) {
            p.x += v.x;
            p.y += v.y;
        });

    auto e = ecs::entity::create()
        .set(Position{0, 0})
        .set(Velocity{1, 0});

    ecs::progress();
    ecs::fini();
}
```

</TabItem>
</Tabs>

## Archetypes in the quickstart

After setting `Position`, the entity belongs to a table whose structural type
contains `Position`.

After adding `Velocity`, it moves to the table for
`{Position, Velocity}`.

The `Move` system's query cache matches that table, so when the system runs it
can access the two contiguous component columns directly.

This is the basic SIECS execution model:

```text
component set
    ↓
archetype table
    ↓
query cache
    ↓
batch iterator
    ↓
system callback
```

Understanding this path makes later API behavior—pointer lifetime, structural
mutation, deferred commands and query performance—much easier to predict.

## Structural versus value changes

This is a value change:

```c
ecs_get(e, Position)->x += 1;
```

The entity stays in the same table.

These are structural changes:

```c
ecs_add(e, Enemy);
ecs_remove(e, Velocity);
ecs_relate(e, ChildOf, parent);
```

They can change table placement.

Systems normally defer structural changes so current table iteration stays
valid.

## C and C++ use the same world

The C++ layer does not maintain a second ECS.

A C component declared in a shared header can be used from C++ and refers to the
same registered component id.

This makes mixed-language modules possible:

- low-level runtime/module in C;
- game/tool layer in C++;
- same entities, tables, systems and resources.
