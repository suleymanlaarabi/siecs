This page is a compact API map. The manuals explain behavior, invariants and
performance tradeoffs.

## World lifecycle

| Purpose | C | C++ |
| --- | --- | --- |
| Initialize | `ecs_init()` | `ecs::init()` |
| Initialize with features | `ecs_init_w_features()` | `ecs::init(features)` |
| Progress scheduler | `ecs_progress()` | `ecs::progress()` |
| Run all systems | `ecs_run()` | `ecs::run()` |
| Run one phase | `ecs_run_phase()` | `ecs::run_phase()` |
| Run one system | `ecs_run_system()` | `ecs::run_system()` |
| Request quit | `ecs_quit()` | `ecs::quit()` |
| Finalize | `ecs_fini()` | `ecs::fini()` |

`ecs_world_feat_desc_t` includes target FPS and worker-thread configuration.

## Entities

| Purpose | C | C++ |
| --- | --- | --- |
| Create | `ecs_new()` | `ecs::entity::create()` |
| Create without reuse | `ecs_new_no_reuse()` | `ecs::entity::create_no_reuse()` |
| Test alive | `ecs_is_alive()` | `entity::is_alive()` |
| Resolve current handle by index | `ecs_entity_from_index()` | `ecs::entity::from(ecs_entity_from_index(index))` |
| Name | `ecs_entity_name()` | `ecs_entity_name(entity.id())` (shared introspection API) |
| Lookup | `ecs_lookup()` | `entity::lookup()` |
| Kill | `ecs_kill()` | `entity::kill()` |
| Mark abstract | `ecs_abstract()` | `entity::abstract()` |
| Get base | `ecs_entity_base()` | `entity.target<ecs::IsA>()` |
| Test IsA | `ecs_is()` | `entity.is(base)` |

Entity handle helpers are `ecs_entity_id(entity)` and
`ecs_entity_generation(entity)` in C. In C++, pass the raw value returned by
`entity.id()` to the same bit-level helpers.

## Components

| Component declaration | C | C++ |
| --- | --- | --- |
| Declare/define | `ECS_COMPONENT_DECLARE`, `ECS_COMPONENT_DEFINE`, `ECS_COMPONENT` | Native `struct` |
| Register | `ECS_COMPONENT_REGISTER(T)` | `ecs::component<T>()` |
| Tag | `ECS_TAG(T)` | Empty native `struct T {}` |

| Core operation | C | C++ |
| --- | --- | --- |
| Add/remove | `ecs_add`, `ecs_remove` | `entity.add<T>()`, `entity.remove<T>()` |
| Test | `ecs_has` | `entity.has<T>()` |
| Required access | `ecs_get` | `entity.get<T>()`, `entity.get_mut<T>()` |
| Nullable access | `ecs_try_get` | `entity.try_get<T>()`, `entity.try_get_mut<T>()` |
| Set | `ecs_set` | `entity.set(T{...})` |

Generic runtime-id operations are `ecs_add_cid`, `ecs_remove_cid`,
`ecs_has_cid`, `ecs_get_cid`, `ecs_try_get_cid`, `ecs_set_cid`,
`ecs_move_cid` and `ecs_modified_cid`. They are the shared low-level API; the
C++ facade uses typed entity methods when the component type is known.

Registration/introspection uses `ecs_component_init`,
`ecs_component_dynamic_init`, `ecs_component_info`, `ecs_component_count`,
`ecs_component_name` and `ecs_tag_init`. Native C++ registration uses
`ecs::component<T>()`; generic tooling uses the shared runtime-id functions.

Requirements use `ecs_with` / `ecs_with_many` in C and
`ecs::component<T>().with<Required...>()` in C++.

## Resources

| Resource declaration | C | C++ |
| --- | --- | --- |
| Declare/define | `ECS_RESOURCE_DECLARE`, `ECS_RESOURCE_DEFINE`, `ECS_RESOURCE` | Native `struct` |
| Register | `ECS_RESOURCE_REGISTER(T)` | `ecs::resource_handle<T>()` |

| Resource operation | C | C++ |
| --- | --- | --- |
| Set | `ecs_set_resource` | `ecs::set_resource(T{...})` or `resource_handle<T>().set(...)` |
| Get | `ecs_get_resource`, `ecs_get_resource_read` | `ecs::resource<T>()` |
| Try get | `ecs_try_get_resource`, `ecs_try_get_resource_read` | `ecs::try_resource<T>()` |
| Test/remove | `ecs_has_resource`, `ecs_remove_resource` | `ecs::has_resource<T>()`, `ecs::remove_resource<T>()` |

The generic resource-id API consists of `ecs_resource_init`,
`ecs_resource_find`, `ecs_resource_name`, `ecs_resource_rid`,
`ecs_try_resource_rid`, `ecs_has_resource_rid` and `ecs_remove_resource_rid`.

## Relations

| Relation declaration | C | C++ |
| --- | --- | --- |
| Declare/define | `ECS_RELATION_DECLARE`, `ECS_RELATION_DEFINE`, `ECS_RELATION` | Native empty `struct` |
| Register | `ECS_RELATION_REGISTER(R)` | `ecs::relation<R>(descriptor)` |

Registration/introspection uses `ecs_relation_init`, `ecs_relation_info` and
`ecs_relation_count`; C++ relation registration is `ecs::relation<R>()`.

| Entity relation operation | C | C++ |
| --- | --- | --- |
| Add/retarget | `ecs_relate` | `entity.relate<R>(target)` |
| Remove | `ecs_unrelate` | `entity.unrelate<R>()` |
| Test | `ecs_has_relation` | `entity.has_relation<R>()` |
| Target | `ecs_target` | `entity.target<R>()` |
| Inherit | `ecs_is_a` | `entity.is_a(base)` |

Id forms are available for generic relation ids.

Storage modes are `EcsRelationDense`, `EcsRelationByDepth` and
`EcsRelationByTarget` in both APIs.

Target-deletion policies are `EcsRemoveRelation` and `EcsDeleteSources` in both
APIs.

## Queries

Create/finalize:

<Tabs syncKey="language">
<TabItem label="C">

```c
ecs_query_id_t q = ecs_query({
    .components = { ecs_in(Position) },
});
ecs_query_fini(q);
```

</TabItem>
<TabItem label="C++">

```cpp
auto query = ecs::query{}.build_handle();
// query_handle finalizes its query when it leaves scope.
```

</TabItem>
</Tabs>

| Component query intent | C | C++ |
| --- | --- | --- |
| Read | `ecs_in(T)` | Callback `const T&` |
| Read/write | `ecs_inout(T)` | Callback `T&` |
| Optional read/write | `ecs_in_optional`, `ecs_inout_optional` | `ecs::optional<const T>`, `ecs::optional<T>` |
| Filter/exclude | `ecs_filter`, `ecs_not` | `.require<T>()`, `.exclude<T>()` |
| Upward read | `ecs_up`, `ecs_up_optional` | `.up<T, Relation>()` plus callback type |

`ecs_out(T)` has no distinct typed callback spelling; a mutable `T&` is
declared read/write by the C++ facade.

| Relation query intent | C | C++ |
| --- | --- | --- |
| Required | `ecs_rel(R)` | `.with_relation<R>()` |
| Exact target | `ecs_to(R, entity)` | `.to<R>(entity)` |
| Depth | `ecs_depth(R, value)` | `.depth<R>(value)` |
| Optional/excluded | `ecs_rel_opt`, `ecs_not_rel` | Test `entity.has_relation<R>()` in a typed callback |

Ordering uses `ecs_order_by_target(R)` / `ecs_order_by_depth(R)` in C and
`.order_by_target<R>()` / `.order_by_depth<R>()` in C++.

Iteration:

<Tabs syncKey="language">
<TabItem label="C">

```c
ecs_iter_t it = ecs_query_iter(q);

while (ecs_iter_next(&it)) {
    void *field = ecs_field(&it, index);
}
```

</TabItem>
<TabItem label="C++">

```cpp
query.each([](Position &position, const Velocity &velocity) {
    position.x += velocity.x;
});
```

</TabItem>
</Tabs>

Iterator-level utilities are `ecs_query_count`, `ecs_field_kind`, `ecs_targets`
and `ecs_target_shared`. The typed C++ facade normally exposes fields through
callback arguments and relation targets through `ecs::entity::target<R>()`.

## Systems and phases

Create:

<Tabs syncKey="language">
<TabItem label="C">

```c
ecs_system_id_t id = ecs_system({
    .name = "Move",
    .phase = EcsOnUpdate,
    .callback = Move,
});
```

</TabItem>
<TabItem label="C++">

```cpp
auto id = ecs::system("Move")
    .phase(EcsOnUpdate)
    .each([](Position &position, const Velocity &velocity) {
        position.x += velocity.x;
    });
```

</TabItem>
</Tabs>

System control uses `ecs_system_name`, `ecs_system_enable`,
`ecs_system_disable` and `ecs_run_system` in C. C++ provides
`ecs::enable_system`, `ecs::disable_system` and `ecs::run_system`; names remain
available through the shared introspection function.

Phases use `ecs_phase` / `ecs_phase_init` in C and the `ecs::phase` builder in
C++. Both APIs use `ecs_phase_name`; C++ runs a phase with
`ecs::run_phase(phase)`.

`ecs_system_desc_t` includes:

```text
name
query
callback
user_data
user_data_dtor
phase
after[]
disabled
main_thread_only
no_defer
interval
```

## Deferred operations

<Tabs syncKey="language">
<TabItem label="C">

```c
ecs_defer_begin();
/* structural operations */
ecs_defer_end();
```

</TabItem>
<TabItem label="C++">

```cpp
ecs::system("DeferredWork")
    .each([](ecs::entity entity) {
        entity.add<Selected>();
    });
```

</TabItem>
</Tabs>

The outermost end flushes the active command buffer.

## Observers and events

Built-in events:

`EcsOnAdd`, `EcsOnRemove`, `EcsOnSet`, `EcsOnRelationSet` and
`EcsOnRelationRemove` are the C event constants. Their typed C++ tags are
`ecs::OnAdd`, `ecs::OnRemove`, `ecs::OnSet`, `ecs::OnRelationSet` and
`ecs::OnRelationRemove`.

Create:

<Tabs syncKey="language">
<TabItem label="C">

```c
ecs_observer_id_t id = ecs_observer({
    .on = EcsOnSet,
    .query.components = { ecs_in(Position) },
    .callback = OnPositionSet,
});
```

</TabItem>
<TabItem label="C++">

```cpp
auto id = ecs::observe<ecs::OnSet>()
    .each([](const Position &position) {});
```

</TabItem>
</Tabs>

Observer control uses `ecs_observer_enable`, `ecs_observer_disable` and
`ecs_observer_fini`. Typed builders return the same public observer id consumed
by these shared control functions.

| Custom event operation | C | C++ |
| --- | --- | --- |
| Allocate/register | `ecs_event`, `ecs_event_register` | `ecs::event<Event>()` |
| Observe | `ecs_observer` | `ecs::observe<Event>()` |
| Trigger | `ecs_observer_trigger` | `ecs::trigger<Event>(entity, data)` |

## Modules

| Module operation | C | C++ |
| --- | --- | --- |
| Declare/define | `ECS_MODULE_DECLARE`, `ECS_MODULE_DEFINE` | Native module type with static `import` |
| Import | `ECS_MODULE_IMPORT` | `ecs::import<Module>(args...)` |

The shared runtime module API consists of `ecs_module_init`, `ecs_module_load`,
`ecs_module_find`, `ecs_module_name`, `ecs_module_enable`,
`ecs_module_disable` and `ecs_module_is_enabled`. C++ uses `ecs::module_ref<T>`
for typed enable/disable/status operations.

## Scenes

Scene serialization currently uses the shared C-compatible API in both
languages: `ecs_save_memory`, `ecs_scene_free`, `ecs_scene_validate`,
`ecs_load_memory`, `ecs_save` and `ecs_load`. The C++ facade does not currently
provide a separate typed scene owner.

Runtime entity handles are remapped on load.

## Component metadata

`ecs_component_info(component)` exposes immutable registered metadata such as:

- name;
- size;
- reflection handle/descriptor;
- inheritance policy;
- debug mutation metadata where enabled.

Use this for tools/introspection rather than reading internal component indexes.

## Relation metadata

`ecs_relation_info(relation)` exposes:

- registered name;
- storage mode;
- target deletion policy;
- acyclic flag.

Generic relation tools should branch on this metadata before offering
target/depth traversal operations.
